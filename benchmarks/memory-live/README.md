After a run, the user must inspect the console COST and **every exact run namespace** breakdown, confirm them, and explicitly authorize cleanup. Rounded unchanged balances are not proof of zero cost. It acquires the same exclusive run lock and durably records the exact run/binding confirmation and hash in the spend authority. An active evaluation blocks authorization. Cleanup validates this authorization before reading credentials and again before each DELETE; historical `cleanupApproved` or shared-account flags cannot bypass it. Missing/corrupt state fails closed.

Only after that explicit user action may an authorized owner invoke scoped cleanup with the original manifest and an explicit cleanup estimate. This task does not run cleanup or grant live approval. The original key-path, account declaration, ownership, namespace visibility and no-`moveTo` checks still apply.

Standalone live cleanup requires an explicit positive `--estimated-cleanup-ceiling-usd` before credential access. Its ceiling covers **cumulative cleanup**, including all prior cleanup and uncertain sends, and can only stay the same or decrease. It cannot exceed the original protected reserve. The original 28-request cleanup allowance is cumulative too; restarting the command never renews either allowance. `requests`/`requestCount` describe the current invocation; `costProgress.cleanupRequestsUsed` and `durableReservations` expose cumulative reservations, including a reservation made immediately before a crash.

Preparation creates private `run-authority.json`, `run-lock.sqlite` and `run-spend.sqlite`. Keep these files and any SQLite recovery journals with the original run. The run lock remains held through in-flight evaluation or the separately authorized cleanup; concurrent invocations reject with `run_in_use` before reading a key. Process exit releases the OS lock without deleting lock files. Evaluation is durably marked consumed before credential access and can never restart, even if ownership/results disappear. Cleanup cannot use an evaluation authority, even after it is sealed. It needs a separately held cleanup authority and durable human reconciliation confirmation.

Missing reporting JSON can be recovered only from the intact, validated durable ledger; present corrupt or contradictory receipts fail closed. Missing/replaced/corrupt durable authority produces an explicit `run_authority_missing_or_corrupt` or `run_spend_*` error before credential access.
