## Why the unchanged contract has no supported solution here

The installed generation declares a real executable in `.mcp.json`; its role files and full file set are hash verified. An unavailable managed binding supplies no replacement. Keeping that plugin active defeats the managed omission; denying it violates spec.md's unconditional pairing rule; changing its files violates generation verification; rejecting the launch defeats the approved optional behavior. The current source has no alternate available binding that resolves those four conditions simultaneously.

## Alternatives evaluated

- **Continue blocking:** safe containment under today's contract, but not optional acceptance. Making this permanent is an additional product change; not recommended or authorized.
- **Publish a new launch-managed Codebase generation:** feasible direction analogous to dynamic web search, but changes native installation/launch behavior and needs reviewed publication. It does not repair optional behavior for the existing verified generation and is larger than a precise omission rule.
- **Empty/fake replacement MCP:** no existing implementation or necessity evidence. It misrepresents pairing unless designed as a new capability transport and still requires native parity work. Do not invent one to satisfy a structural assertion.
- **Mutated/copy-filtered plugin, safe mode, strict MCP config, tool-only deny, or environment redirection:** none is an existing equivalent solution preserving this generation, unrelated native sources, and omission of backend execution. `--strict-mcp-config` excludes other MCP sources; tool permissions alone are not server-load control. No guessed flags are needed.
