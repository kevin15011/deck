# Working Brief: Claude Code runner with shared capabilities

## Status and authority

Installable implementation candidate on `main`, based on `8666619715f0c279e0e7c493575eb93e5f5a24a7`. The expanded candidate has passed independent focused Quality and a full pinned-toolchain test run. This is not proof of live Claude account availability, combined conversational runtime behavior, or macOS execution. This change is separate from the historical OpenCode-only `opencode-supermemory-plugin-profiles` change; its OpenCode process-composition acceptance gap must not be silently closed by this work. Source, current tests, and approved OpenSpec requirements take precedence over this brief.

## Intent and acceptance

Make Claude Code CLI a first-class Deck runner with the current OpenCode experience as the behavior baseline: discover/configure/install/update/diagnose capabilities; materialize the Developer Team, instructions, skills, agents, MCP tools, Web Search, models and applicable execution controls; and launch supervised sessions. Include adaptive memory through the official Claude Code Supermemory plugin, not through a second Deck capture/recall loop.

**User correction:** Installation MUST happen through the existing Deck TUI, once at the Claude user/global runner scope, as OpenCode does with its default `$HOME/.config/opencode` root. The repository root supplies execution context and verified identity, not a destination for Deck-owned agents/skills/MCP files. Do not make `deck claude team`, `deck claude mcp`, `.claude/agents`, `.claude/skills`, or project `.mcp.json` the Deck installation path. Native project-specific Claude features remain unrelated user choices, never Deck's installation default.

- A single Deck Web Search provider selection and credential must serve each supported runner without another user enrollment. Preserve its enabled/disabled state and provider policy; native Claude search must not silently substitute for Deck's configured provider.
- A single Deck adaptive-memory selection and protected credential/profile collection must serve supported runners. Preserve the OpenCode SSH Host alias versus explicit default routing rule, including the fail-closed missing/invalid credential behavior. Evolve the OpenCode-named store by a tested, non-destructive compatibility/migration path; do not make core policy import an OpenCode adapter.
- Deck must supervise Claude launches, verify the enabled plugin/registration and effective configuration, strip inherited memory credentials and tags, inject only the selected credential into that child process, and supply the existing verified canonical `sm_project_v1_<owner>_<repository>` container tag when identity is established. Profile selection and repository identity are independent. No verified identity means no Deck-invented tag; confirm plugin fallback semantics before declaring readiness.
- The official plugin alone owns Claude memory recall, capture, injection, compaction, storage, and memory policy. Disabled memory must not result in a Deck-issued credential or a falsely advertised remote-memory-off state when an external plugin is active.
- Repeated install, update, launch, rotation, failure and rollback preserve unrelated Claude user/project/managed configuration and existing OpenCode/Pi/Codex behavior. No secret appears in settings, arguments, status, diagnostics, captured output or committed files.
- Claim individual capability support only after native materialization **and** actual composed-runner evidence. An unsupported protected control is explicit, never represented as prompt-only equivalent enforcement.

## Evidence and uncertainty

Repository evidence is from current source on `main`. The local knowledge graph is a fast index from 2026-08-20 and is stale for new memory files and changed launch/config files; use direct source and focused tests for implementation. The existing OpenCode release brief (`openspec/changes/opencode-supermemory-plugin-profiles/working-brief.md`) records a v0.6.0 risk-accepted release but does not establish complete combined OpenCode-process readiness.

External primary documentation consulted 2026-09-29 (publication dates not shown): Claude [settings](https://code.claude.com/docs/en/settings), [CLI](https://code.claude.com/docs/en/cli-reference), [MCP](https://code.claude.com/docs/en/mcp), [hooks](https://code.claude.com/docs/en/hooks), [features](https://code.claude.com/docs/en/features-overview) (Context7 plus point extraction), and Supermemory [Claude integration](https://supermemory.ai/docs/integrations/claude-code) and [plugin repository](https://github.com/supermemoryai/claude-supermemory) (point extraction). Claude settings precedence is managed policy > CLI/session > local project > shared project > user, with environment precedence varying by key. Claude supports native agents/skills/plugins/hooks and scoped MCP; project MCP may load without interactive approval in unattended runs. The Supermemory integration documents Node.js 18+, a renamed `supermemory@supermemory-plugins` plugin, `SUPERMEMORY_CC_API_KEY`, and a project `repoContainerTag` override. The OpenCode plugin instead uses `SUPERMEMORY_API_KEY` and Deck's `SUPERMEMORY_REPO_TAG`: these variables must **not** be assumed interchangeable. Moving upstream documentation and a repository README do not prove pinned-plugin precedence, compatibility, artifact integrity, or actual runtime isolation.

## Design decisions, risks and non-goals

Keep canonical configuration, identity policy and credentials runner-neutral; keep Claude-specific materialization, version probes, plugin inspection and launch translation in a Claude adapter. Prefer a narrow extraction of existing profile policy with a non-destructive migration to a shared secret name/schema over wholesale replacement. Config metadata and shared secrets have different storage boundaries; the shell-profile Tavily credential is already global, but process availability and disabled-mode behavior need explicit verification.

Do not overwrite managed settings, silently remove external plugins, persist credentials in `.claude` or `.mcp.json`, or promise that a child process can hide environment credentials from co-loaded hooks/plugins. A conflicting project `apiKey`/`repoContainerTag`, alternate saved auth, ambiguous alias, malformed credential store, missing default, linked worktree, duplicate plugin or unavailable policy hook must fail closed or be visibly reported. The exact Claude plugin revision, authentication/tag precedence, available model surface, policy constraints and cross-runner container equivalence remain open verification gates. A future product decision may be needed if Claude cannot meet a protected execution or credential-isolation boundary; do not silently weaken it.

Non-goals: migrating memory content, implementing another memory provider, changing the official plugin's memory policy, installing into the real user's Claude configuration during tests, and replacing Claude authentication. Sharing Deck setup does not imply that Pi/Codex memory mechanisms are replaced by the Claude plugin.

## Sequence and verification

1. Inspect and pin a published Claude version and official plugin revision; inspect artifact code/manifest and test exact credential, tag and managed-setting precedence in a hermetic fixture. Establish noninteractive install/approval behavior and the protected hook boundary before advertising support.
2. Define a short design/spec for shared profile ownership, legacy OpenCode compatibility, one-setup Web Search semantics, process-authorization rules and per-capability disposition. Keep the existing OpenCode-only change intact.
3. Implement one end-to-end Claude adapter slice: registration and TUI/Doctor, transaction-safe user/global install/update, native team/tools, model handling, plugin inspection, and supervised launch with shared credential/verified tag.
4. Run focused deterministic tests (migration, alias/default routing, worktrees, overrides, plugin conflict, disabled mode, inherited environment scrubbing, redaction, rollback, Web Search reuse, hooks/permissions and protected denial), then an isolated composed Claude process including real plugin recall/capture and cross-runner canonical-container evidence. Check affected OpenCode/Pi/Codex tests and TypeScript; no real credentials or user config writes in test gates.

## Result

### Current expanded candidate (2026-09-30)

The earlier limited milestones below are historical, not current feature exclusions. The candidate now implements:

- Global installation through the existing TUI and operational Claude adapter. Canonical agents/skills, selected native MCP configuration and RTK hooks live in versioned Deck-owned plugin directories, not repositories. Content digests identify immutable versions; owned receipts preserve assignments/selections, repair and deselection work when a previously selected tool disappears, and old versions are retained rather than overwritten.
- Documented Claude model aliases (`sonnet`, `opus`, `haiku`, and role inheritance), per-role assignment persistence, regenerated native model frontmatter and TUI readback. These are supported aliases, not a claim that every model is available to the authenticated account. No Pi/OpenAI catalog fallback. Account-specific effort choices remain unoffered rather than guessed.
- Reviewed acquisition/verification and configuration for Context Mode, native Codebase Memory MCP, Context7, pinned RTK and operation-authorized Serena with proxy revalidation. Investigate/Quality use selected read-only MCP tools in the actual plugin-qualified namespace. Selection survives reopening, including Context7; unchecked package capabilities are actually removed from the next plugin version.
- Shared Tavily Web Search selection/credential reuse, with bounded credential recovery from the existing Deck-owned shell-profile block and process-local handoff rather than secrets in plugin files or arguments.
- Official Claude Supermemory plugin pinned to commit `915aba1b8056ddb3630fa833973032ba6b788fdb`, with integrity verification of its 26 plugin files. TUI activation follows successful reviewed installation and verification. CLI composition reuses the existing OpenCode protected alias/default profile compatibility resolver; provider-specific strings are not placed in Core. The supervised launch rejects conflicting settings/environment, alternate endpoints, duplicate registrations and higher-priority tag overrides, strips inherited memory values, and passes the selected token and existing verified canonical repository tag to the official plugin. No duplicate Deck memory host/capture pipeline is introduced.
- Supervised interactive `deck claude developer` startup selecting the namespaced Lead and loading the verified team/official memory plugins. This is static-compatible/native-permission operation, not strict invocation-scoped authorization. Resume/exec and real account model discovery are not asserted as verified.

Verification: owner focused suites passed 255 affected tests plus 75 related tests before broad regression repair. Independent Quality returned GO after rechecking archive extraction, namespace permissions, selection hydration, manifest isolation, path trust and credential override controls. Lead independently ran 99 selected tests, TypeScript and the opt-in real compiled-canary install smoke in a temporary directory. An initial full suite under ambient Bun 1.4.0 found two task regressions (Core purity and launch fixture hermeticity) and one pinned-toolchain mismatch. Both regressions were repaired without weakening their audits. The final **complete repository suite under existing isolated Bun 1.3.12 passed: 5,079 passed, 2 skipped, 0 failed across 328 files**, 247.07 seconds. The user toolchain was not replaced. `git diff --check` passed. No commit, push or release was performed.

Remaining evidence boundaries: no paid external model calls, real account tokens, user installation or real combined Claude conversation were used. The actual pinned Supermemory artifact passed local plugin validation and its published hooks were exercised against local mock endpoints; that does not establish a live full session. Linux compiled installation was verified; macOS runtime execution was not. Co-loaded Claude plugins share the child process and can see its token, which is disclosed in the review UI rather than described as credential isolation. The official memory plugin can add its own first-run `statusLine` setting; the TUI discloses that upstream effect. A future acceptance of these disclosures is not inferred from earlier OpenCode decisions. The installed user canary is unchanged: the user must rebuild/reinstall it to try this candidate.

### Runtime model discovery correction (2026-09-30)

The fixed alias catalog described above was rejected by the user and is superseded. Model discovery now queries the installed Claude executable with a metadata-only SDK `initialize` control request and reads the `models` response used by `supportedModels()`. There is no inference prompt or fixed catalog fallback. The TUI displays runtime-provided names, exact identifiers, reported effort levels, loading/error/retry states and separately labeled inheritance. Changed assignments are validated against a ready snapshot and the selected exact identifier is safely quoted in generated frontmatter. Existing persisted selections remain readable when discovery is unavailable.

The probe runs with temporary HOME/configuration, disabled customizations/MCP/tools/session persistence and inert model-selection metadata projected from user/project/local settings; no user credentials are copied. Non-managed available-model lists merge and managed lists replace lower scopes, including an empty managed list. Requests are generation-guarded against stale results and subprocess-group cleanup is bounded and covered for success, cancellation and timeout. This is installed-runtime metadata, **not authenticated `/model` equivalence or a guarantee of account entitlement**. A credential-free installed-Claude probe showed a custom native picker entry; a real authenticated selector comparison was not performed.
