# Per-session user message queue

## User outcome and verified entry trace

The user cannot leave messages queued while the Lead is working. The current web composer permits sending during native work, but the host rejects `prompt.send` when `leadBusy(live)` is true with `turn-in-progress`. The UI's single pending prompt also replaces active progress on each submission, so accepting queued messages alone would incorrectly obscure ongoing work.

Provide a bounded per-session FIFO queue for user messages without interrupting the current response or starting concurrent Lead turns. Keep queued messages distinct from messages actually delivered to the Lead. Display pending message previews/order and allow removal before dispatch. Clear the draft only after durable acceptance; preserve it on rejection and across session navigation. Maintain the existing compact composer and status indicators.

## Accepted concurrency and lifecycle decisions

Use a durable session inbox feeding the existing native-turn/global-capacity scheduler. Future messages do not pre-create fake current task attempts. The send command identifier is the stable prompt identifier; durable ledger order defines FIFO. All send acknowledgements report accepted queued state without waiting for native admission; audit and adapt existing CLI consumers rather than fabricating an attempt for compatibility. Enforce 32 pending messages, 1 MiB aggregate pending UTF-8 text and the existing 262,144-character individual limit before acceptance. Queue acceptance and retries require durable identity deduplication even after receipt eviction.

Allow `prompt.cancel { promptId }` before actual native admission, including a materialized turn waiting for global capacity; cancellation and admission must have exactly one winner. User FIFO work takes precedence over new internal wake reservations. An internal wake already reserved or preparing before the user message was accepted may finish; enqueue does not preempt that reservation. This scheduling ownership avoids abort/reprepare churn and is distinct from the native-admission fence used for user delivery and cancellation. Pending child notices keep their existing provenance and delivery accounting; they must not be duplicated or rewritten as user text. A bounded notice payload consumes only the notices actually included; overflow remains pending.

Interrupting or cancelling the current Lead persists a queue pause before aborting its current work. Cancelling a child does not pause the Lead inbox. `prompt.resume` clears that single session-level pause and continues remaining messages only after old native ownership settles. Sending while paused adds to the queue without silently resuming. Execution or admission failure pauses remaining work to prevent a failure cascade; resume never retries the failed message implicitly. Closing the session cancels its pending inbox. Assignment changes are blocked while inbox or active/uncertain work exists.

Graceful daemon shutdown preserves never-dispatched entries. Recovery may automatically drain those entries only when the session is enabled and provably settled and no durable pause applies. Never automatically replay an already dispatched/uncertain native attempt: native exactly-once execution cannot be guaranteed across an ambiguous process crash. Reuse existing recovery barriers and durable dispatch fences; do not introduce a general storage transaction engine without evidence it is needed. Durably paused/ownership-blocked inbox entries alone are not native running work and must not prevent a restart required for recovery.

## Exact integration contract

- Send acknowledgement: `{ promptId, state: "queued", position }`, including an idle session. An acknowledgement does not mean the native runner has started.
- Events: `prompt.queued { promptId, text, by, generation, position, createdAt }`; `prompt.dispatched { promptId, taskId, attempt }`; `prompt.state { promptId, state: completed | failed | interrupted | cancelled | ownership-unsettled, reason? }`; `prompt.queue { paused, reason? }`.
- Query: `GET /api/sessions/:id/prompts` returns `{ seq, paused, pauseReason?, queued: [{ promptId, text, createdAt, position }], active?: { promptId, taskId, attempt, state: "dispatched" }, limits: { maxPending: 32, maxBytes: 1048576 } }`.
- Commands: `prompt.cancel { promptId }` and session-scoped `prompt.resume {}`.
- A global-capacity waiter stays in the queued projection until native admission. Only admission appends its actual user chat message, with `data.promptId` for exact correlation.
- The self-sufficient queued event precedes its receipt and explicit log flush precedes acceptance. Dispatch and pause fences flush before native invocation or abort. Existing JSONL `appendMany` is not treated as crash-atomic; recovery handles committed prefixes conservatively.

The native-admission fence is immediately before `startTask`, after awaited runner probe and managed-tool preparation. Merely reserving scheduler capacity is not admission: the item remains cancelable and its notices remain undelivered through preparation. Recheck cancellation and ownership at that final fence. Ownership-unsettled is a waiting barrier and must retain every never-dispatched item; it is not a reason to consume the head as failed.
