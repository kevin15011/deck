# General session permissions — implementation handoff

Recommend host-owned, versioned permission scopes bound to the configured actor. Keep native replies action/turn scoped so Deck retains revocation control. A session grant means repeated authorization within a disclosed scope for the canonical session authority, including reconnect and host restart; it does not mean permission for every action. Implement as a delta after owner127's intrinsic coordination candidate. No new runner implementation is required.

## Minimal canonical contract

Add one host permission-policy module and additive shared types; do not create a generic policy engine. Keep Codex wire decoding in `codex_protocol.rs`, tagged dispatch in `native_approval.rs`, and matching/lifetime/actor policy in the host module.

1. `PermissionRequestV1`: validated effect category, complete material descriptor, issuer binding, actor binding, and immutable request correlation. Decoder returns evidence; host derives authority from persisted ownership and admission. Unknown material fields disable broader reuse rather than being dropped.
2. `ActorBindingV1`: project binding, canonical session ID, canonical session generation, revocation fence, configured role, assignment revision and admitted assignment/policy fingerprint. Lead is its own actor. Member role comes from stored task owner and attempt assignment; never from tool arguments, model text or browser fields. Use existing session-wide assignment revision initially: any assignment edit invalidates new scoped grants, with that boundary disclosed. This avoids a separate per-role epoch migration.
3. `ScopeV1`: tagged, versioned material scope from the table below. A grant stores actor, issuer, scope-policy version, selected scope, source decision and original delivered consent. Scope comparison is containment, never fuzzy text matching. A hash identifies the validated structured object; a hash alone does not define containment.
4. Persist the selected scope alongside the source decision/resolution, retaining the original raw envelope and historical identity. Reuse existing receipt persistence first; no separate grant database is necessary. Each automatic reply records `reused_grant_source` and its scope version. It is an AllowOnce delivery, not a new consent extending lifetime.

The actor deliberately excludes task text, receipt/attempt UUID, thread/turn/item/RPC ID, native PID and transport connection. Those identifiers still MUST match the current request at release. This permits another attempt or task for the same configured role without transferring authority to another role. Role consent never supplies a task's missing modification authority, project trust, dependency resolution, or protected-effect approval.

Issuer binding includes integration/transport, effective execution environment and admitted capability identity. For MCP include configured server identity and tool/schema identity, not just a display name. Compare the effective admitted session epoch; do not trigger full discovery or provenance scans at every grant lookup. Reconfiguration or an unknown identity requires fresh scope qualification. No cross-transport equivalence is inferred in this Codex delivery.

## Scope choices and matching rules

Always offer Deny and Allow once where currently valid. Offer the following session choices only when the host can construct and validate them. Exact reuse remains a useful explicit fallback; it must be labeled as exact.

| Category | Session choice | What can vary; what remains bound |
|---|---|---|
| Command | **This exact command**, plus an explicit **This command prefix in this directory** when qualified | Exact includes command, cwd, environment, execution kind, extra permissions and network context. Prefix uses an argv-vector prefix and exact cwd/environment/permissions, with suffix variability explicitly disclosed. Never derive it by string `starts_with`, trim a shell wrapper, or trust `commandActions`. See qualification below. |
| Native file changes | **Edits to these files**; optional **Edits under this selected folder** | Patch contents may vary. Every source/destination path and operation must fit the chosen scope. Default scope is the displayed finite file set with update operation; create/delete/move are separate explicit operations. Folder scope is an explicit broader choice, never inferred from one file or native `grantRoot`. |
| Permission profile | **These capabilities** | Normalize supported filesystem access/path sets and network capability; subsequent request must be a subset under the same cwd/environment. Read does not imply write, unknown fields/globs/special roots do not silently match, and any deny constraints remain binding. A native boolean network capability must be disclosed as network access, not an invented host-only restriction. |
| Native MCP | **This tool with these constraints** | Bind configured server/tool/schema and material input. For a host-owned, versioned operation policy, permit only listed variable fields, e.g. search query within a fixed project/resource. Unknown tools keep exact canonical input reuse. Do not strip arbitrary fields named `id`, `requestId`, `task`, `path` or `arguments`. |
| Deck permission relay | Same category choices when the registered relay operation has a validated typed effect; otherwise **This exact request** | Bind actor and relay operation identity. Tool names such as `command` or `Bash` supplied by a model are not sufficient to claim a registered operation or parser. Top-level `tool_use_id` is correlation; nested `input` remains material unless a specific operation policy says otherwise. Questions cannot create grants. |
| Intrinsic coordination | No permission grant | Preserve owner127's exact eligible operations and effect-time host checks. Delegating or reading a report does not authorize command execution, file writes, integration effects, or the permission requested through a relay. |
| Reviewed single-file workflow / protected effects | Existing per-action decision | Preserve the explicitly reviewed before/after contract and destructive Git confirmation. Do not let a generic file/command/tool session grant satisfy these separate gates. |
| Existing OpenCode path | Preserve exact behavior and isolate its decoder | No new cross-runner grants or member support inferred. New common types must deserialize safely; native qualification remains deferred. |

Command prefix qualification: initially require a native-offered prefix, explicit user selection, and a small fail-closed host decoder for one simple argv command. Reject shell operators, substitutions, redirects, stdin injection, environment assignments, dispatch/interpreter wrappers and ambiguous syntax. Validate the entire command and permitted suffix form, not merely its first tokens. Do not offer a general `git`, shell, interpreter, install/publish, or destructive-command wildcard. A bounded policy such as `cargo test` can intentionally authorize running project tests with documented argument constraints; it is not a promise that test code cannot have effects. Native sandbox and independent child-effect checks remain active. If reliable extraction is unavailable for a command, offer exact reuse. Broad arbitrary shell authorization is outside this correction, not a prerequisite for it.

For file scopes, validate canonical path containment, relative paths against admitted cwd, existing-parent resolution for new files, symlink escapes and both ends of moves at release. Preserve protected-path policy and the native sandbox; approval-time containment alone cannot promise filesystem race isolation. Match against the complete correlated item, not whichever paths appeared first. Implement the same bounded proposal correlation for members before advertising member file scopes. Missing/incomplete item evidence permits no path-based session grant.

For generic MCP, no trustworthy tool effect schema means no inferred tool-wide authority. A narrowly registered operation policy is the smallest useful broadening mechanism; tool annotations such as `readOnlyHint` do not establish it. Support exact canonical payload reuse for all identifiable requests, including writable members. There is no safe generic distinction between a volatile ID and a resource/account/recipient ID without operation semantics. A later request for “all arguments of any tool” is a separate material product choice; it need not block these improvements.

## Consent, delivery and lifetime

Expose a host-generated list of scope options with opaque IDs, validated bounds and short descriptions. The response selects an offered option ID plus existing decision revision and idempotency command ID. The browser cannot submit a free-form scope, actor or executable prefix. Store and revalidate the exact offered object; stale selections fail without changing consent. Legacy clients submitting bare AllowSession retain exact semantics, never the new broader default. Unsupported/malformed scope metadata disables that scope only, not deny/once.

Example wording: “Allow edits to these 3 files for Apply Deep in this session.” Describe restart survival and revocation in the same compact permission view; keep assignment hashes/correlation in details. Native persistent command-prefix consent remains a separate clearly labeled choice stored by Codex outside Deck's revocation control. Do not translate Deck session scopes into native persistent amendments or `acceptForSession` caches.

Activate a scope only from explicitly selected consent recorded Delivered/Settled with delivery evidence under the unchanged authority fence. Pending, Responded, Dispatching, uncertain or invalidated responses are not grants. Preserve the existing uncertainty contract: a delivered response is not proof the effect completed. The relay currently records delivery before its HTTP result reaches the caller (`session_mcp.rs:700`); do not reinterpret that as client acknowledgement or replay a lost response's effect. A new still-live request may use durably established consent, but uncertain earlier work remains governed by recovery.

At request admission and immediately before release, check current actor/assignment, session generation/fence, issuer/scope containment, source consent state, live exact request ownership, project trust, role restrictions, dependencies, cancellation and existing protected gates. Serialize final authorization/dispatch intent with revocation using the store boundary. Recheck automatic replies too. Concurrent pending requests are separate decisions: after the first scope becomes active, reconsider matching live pending requests under these checks so already-open prompts do not require duplicate consent. Never overwrite an explicit denial or resolved response; never re-execute an old request. Each native response still targets one immutable RPC request.

Reconnect, new native process and host restart preserve consent when canonical authority and issuer remain equal. Ordinary attempt/connection IDs do not expire it. Existing recorded native-context reseed (`session_contract.rs:392–428`) changes canonical generation and invalidates it; preserve that behavior and report the reason for renewed consent. A fresh member process is not itself a canonical session reseed. Assignment changes invalidate new scoped grants through the revision boundary. Session close/delete removes future use without deleting audit evidence.

Revocation advances the existing durable fence atomically and invalidates unreleased matching responses. Already Dispatching effects may have happened; interrupt affected execution and settle uncertainty without replay. Native permission-profile responses are turn-scoped and can have already expanded that turn's authority: revoke must stop/settle that affected turn before claiming the permission is withdrawn. Do not promise retroactive rollback or zero-latency cancellation. Retire only affected retained context when required; preserve unrelated warm sessions and ordered input.

Enable member exact consent/reuse only through this matcher, retaining read-only role restrictions. Record source grant on automatic decisions. This fixes actor leakage and member coverage before broadening.

Each option ships with matching disclosure and tests. Keep fallback limits visible. Do not call the first exact-only slice the complete general correction.
3. Preserve old decisions verbatim. Unversioned historical grants match only their old exact identity/transport plus a provably reconstructed original actor and equivalent complete material evidence from the retained source envelope. In particular, an old command identity omitting extra permissions cannot authorize a new escalation merely because command+cwd match. Never convert old grants to a prefix, path set or tool grant. Derive actor from retained source task/attempt admission; if unavailable, retain the record for audit and require new consent rather than guessing Lead. Existing delegation-role records remain historical; intrinsic coordination does not rewrite or expand them. Unknown future scope versions fail closed for reuse. Additive fields must preserve supported persisted/API decoding; old-client responses cannot select new scopes accidentally.
4. Qualify the combined runtime/UI candidate, then Lead handles installation under existing authority. This report authorizes no install, browser/provider run or real grant mutation.

No additional product answer is needed for these conservative options. Session-wide cross-role inheritance, arbitrary shell families and unconstrained third-party tool trust would require separate explicit choices, and are excluded from the recommended default.
