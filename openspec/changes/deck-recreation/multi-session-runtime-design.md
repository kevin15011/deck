## One implementation slice

Split the existing ownership at its actual lifetime boundaries, without introducing a generic runner framework:

1. **Process entry:** child/process group, stdin writer, one continuously draining reader, global RPC sequence/pending requests, initialization and live account identity, compatibility fingerprint, generation, lifecycle reservation and resource accounting. It lives in shared `Inner`, not the selected project view. Only this owner kills/reaps the process; dropping an attempt cannot kill siblings implicitly.
2. **Thread entry:** immutable `(Deck session, project identity/root, session epoch, native thread ID, process generation)`, thread-config fingerprint, retained transport, acknowledged policy/model, admitted MCP baseline/catalog timestamp, thread-owned resources and idle deadline. Start with connected Lead sessions without process-bound role hooks, matching current fast-path eligibility. Restricted members and other runners retain their current execution path without evicting unrelated warm Leads.
3. **Attempt lease:** receipt/task/attempt/generation, fresh private `session_mcp::Bridge`, current grants/revocation/cancellation state, current turn ID, response routing and timing. It activates only the selected thread's retained transport and closes before completion is published. It never supplies a fallback destination for an unrecognized call.

Keep one `Transport` instance with a distinct stable token/endpoint per retained thread. This reuses its current immutable-call gate rather than changing a global endpoint's current-session pointer. Its config goes into that thread's initial MCP overrides; `/codebase` belongs to the same thread and routes to that attempt's project-bound freshness backend. Idle transport denies calls. A per-thread endpoint is routing separation, not authorization: native metadata, trusted events and live Store checks remain required.

Move RPC response demultiplexing and lifecycle events into the process reader. Route native requests/events by registered thread and, where required, turn; correlate outbound RPC IDs process-wide. Observe each trusted MCP event in only its owner's gate. Resolve unmatched/late requests with a safe protocol denial/error or fail the process closed; never send them to the currently selected UI session. Consume idle lifecycle/status notifications continuously, with bounded queues and explicit overflow handling. The current reader's 256-item queue cannot simply accumulate every idle thread's events until another message.

## Compatibility and admission

Use two fingerprints. Do not merely delete `project` and `session` from today's reuse key.

**Process compatibility:** same qualified executable identity/digest, auth scope/CODEX_HOME and observed account identity, inherited environment, actual spawn cwd/CLI overrides, process feature flags, hook mode, shared provider/managed-policy/config generation and shared native service policy. Connected/restricted/tool-only modes and hook variants are separate groups. No process-global config writes, feature toggles, skill-root replacement, MCP reload, account login/logout, or environment mutation on behalf of one thread inside a shared group.

**Thread compatibility:** immutable session/project/epoch plus complete requested effective thread configuration and role/instruction provenance, MCP overrides, managed helper selection, sandbox/approval policy and assignment. Differences in qualified thread-local fields may coexist in separate threads. Initially qualify cwd/environment, model/reasoning, permission policy, instructions and Deck-owned MCP endpoints. For any unclassified project override or unqualified external MCP/plugin behavior, conservatively choose another bounded process group; preserve earlier groups. Different project paths alone are not incompatible. Compare normalized effective configuration and provenance, not file metadata from A assumed to describe B. Keep secrets out of logs/fingerprints exposed to users.

On a compatible loaded continuation, verify current ownership/project, executable, role/config provenance, grant state and native `account/read`; preserve account-change rejection and permission/model acknowledgement. Rejoin by thread ID without pretending config/developer instructions are updated, or use an already loaded handle with equivalent current acknowledgements. Existing supported turn-level assignment may be used only with its acknowledgement checks. A changed thread contract must retire/reload that thread before dispatch. Do not let retained instructions or permissions silently lag a new contract.

**Separate `process_reused` from `thread_reused`.** A newly created B inside A's existing process still needs its own full cold catalog validation. Only a known loaded thread with a matching contract and its own admitted baseline may use the existing named-server readiness fast path (`native.rs:978-982,4322`). Never lend A's baseline to B. Preserve the current timestamped catalog/native-plugin-refresh semantics; no frozen-plugin promise or repeated broad inventory on unchanged warm A is introduced.

## Lifecycle, bounds and recovery

- Keep native subscriptions while retained. Maintain a separate 30-minute idle deadline per thread, reset after its successfully settled turn; browser navigation and another session's activity do not refresh or evict it. Active/approval-pending work never expires. Timer work carries session/thread/process generations and compares the current deadline under the same lease lock as acquisition.
- Set `thread_unload_delay_secs=0` through the **initial per-thread request override**, then let Deck own the 30-minute timer. On expiry/restart, close attempt authority first, mark that thread retiring, unsubscribe, and await native `thread/closed`/confirmed absence plus relevant tool settlement before releasing its resources. Zero-delay unload is source-supported but must receive the pinned-wire canary below. If qualification fails, wait through the native grace period and keep a counted retiring entry; do not fake completion.
- Session restart keeps durable command idempotency, disconnect-resistant worker ownership, epoch fencing and the active/queued/uncertain-work checks. Retire only the target thread. Increment its epoch after settlement; next explicit message resumes history cold. Keep B's ID/process/epoch intact. A same-epoch retry after a lost HTTP response must not restart B or create a second A. Session release/removal should use the same targeted retirement. Management/login/update/shutdown still drain all affected process groups before exclusive maintenance.
- Cancellation routes `turn/interrupt` to the exact thread/turn. Revoke only that attempt immediately; await terminal settlement, then discard or retain the affected thread according to the existing safe completion policy. Acknowledged interruption need not kill idle siblings. Timeout, malformed shared protocol, EOF, failed process health or unprovable isolation retires/quarantines the whole group: invalidate all leases and loaded handles, preserve completed history, mark dispatched unsettled work uncertain, and require explicit next input/recovery. Never replay a prompt to repair a process.
- Suggested initial policy: **8 retained thread slots total, at most 4 process groups**, including loading/retiring reservations. These are proposed tunable limits, not measured optimal values or native limits. Evict least-recently-settled idle threads under capacity pressure; never evict active, queued-reserved, approval-pending or uncertain ownership. Record the capacity reason; the 30-minute window is an idle maximum subject to this explicit bound. If no safe victim exists, use the existing queue or return a clear capacity result. Never temporarily exceed limits during replacement. Empty groups terminate with observed settlement. Count thread-owned helper processes/temp resources; avoid the current process-wide `retired_paths <32` rule evicting unrelated sessions. Release resources only when their owner is settled.
- Shared auth reservations must remain held for every retained process and retiring worker, even when the scheduler's active map is empty (`runner_management.rs:589-614`). Scope maintenance remains broader than one thread. Global account/provider changes invalidate all affected groups. No credential copies or host-written global profile changes.

Native startup can itself persist implicit project trust when an untrusted cwd is given write-capable permissions (`thread_processor.rs:1458-1531`); that is existing native behavior, not a new Deck permission grant. The same-process test should use already trusted disposable projects and verify that this slice introduces no global configuration edits. Preserve existing native plugin/auth behavior and do not silently broaden trust to make sharing pass.
