## What actually serializes today

1. `session_tasks.rs:535-635`: every accepted member creates a waiting worker. Its 100ms loop claims Preparing only if no task anywhere is Preparing/Dispatching/Running/Cancelling/Uncertain and it is the first accepted attempt in task row order. `tasks.rs:43-56` orders tasks by rowid, so this is not fair attempt-arrival order across sessions or continuations.
2. `server.rs:245-280`: connected members already receive separate worker identities `child:<attempt>`. Their cancellation receiver is discarded; member execution polls durable cancellation. Removing only the global predicate would allow unbounded launches without a scheduler lease.
3. Root serial gates also exist in `server.rs:426-451,926`, `sessions.rs:161-177`, and `lib.rs:757-770`. `clear_active` starts only the first pending task and then pumps roots. Consequently a completed member cannot wake a Lead while another member remains active. Outcome enqueue is already exact-attempt/idempotent (`session_tasks.rs:1163-1240`); keep it, but stop tying wake eligibility to global child emptiness.
4. `server.rs:35-60` shares `Inner` across all project views: Store, active workers, retained natives, authentication scope, credentials and history. `for_session` derives execution project from durable ownership. The single `Mutex<Store>` serializes short SQLite operations; it is not held over the member's model turn. `save_normal_task` wraps report plus terminal-event publication in one savepoint (`session_tasks.rs:905-943`). Keep these atomic writes; do not replace them with unlocked whole-object writes or multiple independent connections to obtain parallelism.
5. `native_reuse.rs:10-38,181-268` holds idle Native entries only. Taking a Native removes it from capacity accounting. The retirement mutex spans asynchronous settlement, but no durable/registry entry describes every leased/loading Native. This is adequate only under the current one-Lead scheduler. Two simultaneous take/park paths can miscount threads/groups, fail to find a compatible active group, or retire a group whose other thread is active. `common_key` invalidation and epoch retirement also need active-group awareness.
6. `native_process.rs` already has a continuous reader, process-wide RPC IDs, per-thread bounded event queues, short route/pending locks and a writer lock held only while writing a message. This is useful routing infrastructure, not proof of production simultaneous turns. Overflow/EOF/RPC timeout calls `fail`, revokes every route and kills the group. `Native::drop` also fails a shared group (`native.rs:105-120`); `Native::terminate` is process-wide. A borrowed thread must never use those as ordinary sibling-safe cancellation.
7. Members currently create `Bridge::start_member` and `Native::start_member`, run their own reader, then terminate and reap that process before publishing a successful terminal report (`session_tasks.rs:657-804`; `native.rs:4043-4080`). The bridge has its own listener/token and immutable task/attempt binding (`session_mcp.rs:15-115,194-219`). Member startup selects process feature flags for read-only roles and supplies an attempt credential through child environment (`native.rs:225-355`). Those inputs are process-scoped: a writable member, restricted reviewer and Lead cannot simply share this process policy.
8. Restart currently rejects any active worker globally (`session_epoch.rs:180-213`), even in another session. Auth management uses shared execution and exclusive maintenance locks (`runner_management.rs:589-614`). Host shutdown sets cancellation and signals workers (`server.rs:457-489`). Recovery currently marks undispatched members Cancelled without distinguishing a previously spawned preparing process (`lib.rs:601-614`); concurrent recovery must retain ownership evidence independently of dispatch evidence.

## Scheduler and ownership algorithm

Use the existing shared active-worker boundary as the serialization point, adding typed owner/lease metadata rather than separate competing queues. Each claim binds `(project, session, logical task, attempt, execution generation, owner role, runner, pool, native process generation when known)`. Retain command IDs, original source bindings and recorded assignments.

1. Reconstruct occupied slots from durable attempts/receipts and live worker leases before admission, including unopened sessions and recovered uncertain owners. Deduplicate the same owner across both sources. Accepted waiting work is not a native execution slot; preparing work is. Cancellation, model completion or a UI disconnect does not itself release a slot.
2. Under the admission lock and Store lock, choose the next eligible session by per-pool round robin, then its earliest eligible attempt by persisted acceptance order (stable sequence preferred; timestamp plus stable tie-break only if order is unambiguous). Do not prioritize a continuation merely because its task row is older. Recheck authority, dependency revisions, original binding, policy and cancellation; snapshot current approval mode at this claim, preserving recorded assignment. Persist Preparing/claim identity before external launch. Reject an invalid candidate explicitly and continue scanning; unrelated ready tasks must not suffer head-of-line blocking.
3. Reserve execution/process capacity and register one worker before releasing the locks. All paths—browser submission, queued roots, member tool admission, outcome wake and recovery—use the same claim policy. On failed persistence, do not spawn. Spawn failures settle or retain the lease truthfully. A duplicate wake/retry finds the existing attempt lease.
4. Start asynchronous preparation without Store, history, credential or scheduler locks held. Replace one polling task per accepted attempt with a bounded pump woken on durable acceptance, completion/drain, cancel, decision/dependency resolution and relevant configuration changes. Existing queue rows are the waiting state; no second unbounded mailbox.
5. Publish terminal report/event under the existing transaction only after model/process/tool settlement as appropriate. Then release the native lease and pump both pools. Retained healthy Lead processes release the execution slot but keep resource/auth ownership and a 30-minute per-thread idle deadline.

Preserve the existing lock order: admission/active → history when needed → Store → auth scope. Other paths may take a subsequence, never an inverse while holding a lower lock. Runtime registry locks must be short and released before Store callbacks, network I/O or native settlement; obtain a generation-bound reservation then perform the async work. Preserve history-before-Store in original-source operations. Do not hold the stdin writer mutex while awaiting a reply. Storage failure remains host-wide fail-closed; a member panic/transport loss is owner/group-scoped unless persistence itself failed.

### Resource policy

Execution budgets and retained-cache bounds are different resources. Four retained groups must not consume all slots needed by children of an active Lead. For default 2/4 execution pools, a concrete conservative envelope is: at most 4 retained Codex groups, 4 dedicated member processes, and 2 non-retained Lead processes for modes that cannot use the retained pool — **10 top-level native processes maximum**, including retiring/uncertain reservations. Retained groups include their active Leads; do not count them twice. At most 8 retained-thread entries plus 4 member and 2 non-retained Lead entries. Slice A has only one Lead execution slot. These are proposed resource limits derived from the chosen placement, not a measured optimal setting or a native restriction.

Resolve configured budgets through the canonical config/compatibility source; do not introduce hidden env overrides or write global runner profiles. Explicit nondefault budgets must be validated together with the corresponding resource envelope; decreasing limits never kills active work, increasing them cannot bypass native resource admission. Keep current 32 waiting root inputs, 64 tasks/session and 32 attempts/task bounds. Avoid a new unbounded queue of spawned waiters. Helpers, listeners, temporary paths and pending approval waits belong to their thread/attempt leases; count owned managed backends and record process-tree/RSS/FD peaks in canary evidence. Arbitrary plugin descendants mean a top-level process cap is not a claim of an OS-wide process or memory cap.

Only safely settled idle retained entries are LRU eviction candidates, under the existing explicit capacity exception to the 30-minute idle window. Parallel member launches should not evict the warm Lead cache. No active, approval-pending, loading or uncertain entry may be evicted to manufacture capacity. Capacity remains counted until native exit/unload and owned helper cleanup are observed.

## Authority, cancellation and recovery invariants

- No UI selection or mutable global current-task pointer participates in routing. Dedicated members keep independent pipes/RPC namespaces, tokens and project-bound bridges. Shared readers require process-wide RPC IDs and exact thread/turn routes; requests lacking an attributable identity cannot borrow the newest attempt. Same call IDs, identical arguments or matching role names never merge authority.
- Preserve `session_mcp::live`, role/config verification, immutable assignment, current generation/grant checks and final checks before effects. Native metadata is correlation evidence, not a grant. Per-attempt bridge credentials and stable retained transport credentials are distinct. Auth read remains live each turn; unchanged warm Lead continuation uses its own admitted catalog, not another thread's inventory. New threads still cold-validate.
- Decision responses bind root/task/attempt/generation/thread/turn/request/revision as today (`decisions.rs:384-430`). Completing or cancelling A invalidates only A's outstanding replies. A stale A approval cannot authorize B, a continuation, or a retried RPC. Root cancellation retains its intentional descendant-cancellation semantics, distinct from target-member cancellation; ordinary Lead completion does not revoke independent admitted children.
- Cancellation first revokes attempt effects and records intent, then interrupts/drains the owned native work. Dedicated member termination may kill/reap only its own process group. Preparation cancellation must either drain its in-flight request to a known boundary or explicitly settle that dedicated process; never drop the worker and release capacity while cleanup continues. Propagate cancellation into preparation, not just the post-start event loop.
- Model completion is not process settlement. Keep uncertain ownership counted after a drain deadline or unexpected worker exit; no permit release through an unobserved RAII drop. Separate execution outcome uncertainty from confirmed process settlement in evidence. Retain the original task's conservative recovery requirements; do not automatically retry an uncertain prompt.
- For shared Leads, normal target cancellation uses exact thread/turn interrupt and target retirement. EOF, corrupt routing, queue overflow, partial write/RPC timeout or unknown load identity retires the group and revokes all its routes. Persist affected attempts individually as uncertain when dispatch may have happened, invalidate retained siblings and preserve another group's work. Do not mask group failure as a successful isolated cancellation.
- Shutdown first closes admission for both pools and rejects bridge effects, then cancels/drains all live owners and retained groups; authentication/maintenance reservations survive until actual settlement. A native process group and its helpers cannot disappear from accounting merely because the HTTP request or scheduler worker ended.
- On restart, no dispatched input or native approval is replayed. Recover every owner, not just the latest visible session. An undispatched Preparing attempt with a recorded spawned process is not proven process-free; preserve an ownership reservation until inspected/reaped even if its input outcome is safely Cancelled. Brand-new accepted/no-process work may follow the existing cancelled-on-restart policy. Session restart, host recovery, process loss and maintenance are distinct operations.
