# Working Brief: OpenCode Supermemory Plugin with SSH-Alias Profiles

## Status

Implementation candidate on `feat/opencode-supermemory-profiles`, based on fetched/up-to-date `main` (`b67e35c`), currently **NO-GO** for full OpenCode-process readiness. The user explicitly chose to retain all normal global/project plugins in the managed OpenCode process, accepting that co-loaded trusted plugins can access the selected process credential. No live user installation, credentials, or successful combined OpenCode-process runtime verification has been performed. The formal proposal/spec/design/tasks in this change define an OpenCode-only supersession boundary upon approval; this incomplete candidate does not yet replace active or promoted memory requirements.

## Intent

For Deck-managed OpenCode developer sessions only, let the official Supermemory plugin own all adaptive memory effects: recall, capture, injection, compaction integration, storage, and memory policy. Deck installs/configures the plugin through its TUI, stores user-configured credentials keyed by Git SSH Host aliases plus a default, selects the credential and supplies its existing canonical `sm_project_v1` tag only when repository identity is verified, and does not mediate memory traffic. If identity is not verifiable, no Deck tag is passed and the plugin chooses its fallback. Other runners and Context Mode's local/indexed knowledge role remain out of scope.

## Provisional acceptance

- The TUI discovers eligible literal SSH Host aliases as labels without opening or displaying private keys. Users explicitly associate each profile and optional default with a validated API credential; secrets never appear in OpenCode config, process arguments, logs, or diagnostics.
- Launch examines the logical Git origin remote only to route the credential. An exact configured SSH alias selects its token; whenever no specific profile can be resolved (including HTTPS, absent origin, unknown or ambiguous SSH alias), Deck passes the configured default token. Do not silently infer a personal/corporate profile from a key filename, Git author, or repository scope.
- A Deck-managed OpenCode child process receives only the selected credential. When neither a specific token nor a default is available, do not silently fall through to unrelated global config, browser login, or inherited environment credentials: present a clear diagnostic and require an explicit choice about disabling memory or stopping launch. Direct OpenCode launches and unrelated projects must not silently inherit a Deck-managed credential.
- The pinned official plugin, Deck execution plugin, RTK, and the configured Context Mode route coexist. The user explicitly selected the stable binary's static-compatible Apply mode, which lacks Deck invocation-scoped denial but retains OpenCode-native permissions; do not claim equivalent strict-mode security. Repeated turns, child sessions, resume, abort, and compaction must not duplicate memory effects or cross personal/corporate profiles.
- For OpenCode, eliminate Deck-owned Supermemory host/loopback/recall/capture/injection, memory policies and advisory memory instructions while reusing only the pre-existing trusted owner/repository tag computation. Deck must not migrate, copy, or interpret memory content. Existing promoted requirements require a formal replacement/change; this brief alone does not supersede them.

## Design questions and protected risks

1. User decision: an unresolved specific profile (including an unknown or ambiguous SSH alias) routes to the configured default. This fallback intentionally cannot infer personal versus corporate identity; surface the selected profile identity clearly in the TUI/launch preview without displaying secrets.
2. User decision: Deck is a plugin installer, credential router, and provider of its pre-existing verified canonical repository tag; Supermemory alone owns memory lifecycle and content. No Deck memory bridge, migration or dual-writing for OpenCode. Existing memory remains under its previous provider/container unless Supermemory itself exposes a separate user-initiated migration.
3. Pin target OpenCode generation and a published plugin version/entry point; inspect the shipped artifact and test it in an isolated runtime. Browser-login precedence, credential fallback, supported account switching and process/env behavior need verification before promising isolation.
4. User decision: preserve existing global/project plugins in Deck-managed OpenCode sessions instead of isolating the plugin set. The selected token is shared with co-loaded plugin code in that process; document the trust boundary. This does not authorize installation into unrelated sessions, use of another account's global credential when no selected token exists, or forwarding the token to an unrelated API endpoint.
5. When neither the matching profile nor a default token exists, block the managed launch rather than silently select another credential source. Keep Context Mode as MCP; do not disable it solely based on an untested claim of conflict.
6. Published `opencode-supermemory@2.0.15` directly conflicts with the effective OpenCode 1.18.31 loader (`server()` expected; published `./server` exposes `setup()`). The earlier 0.1.8 initializes but lacks automatic session/turn capture and can prefer a config-file API key over the selected environment key, so it is **not** an acceptable replacement. A small Deck-owned loader-only adapter forwards `server()` to the official 2.0.15 V1 implementation and `setup()` to its V2 implementation; published-artifact hook-level tests demonstrate capture/compaction without Deck-managed memory hooks. Actual OpenCode-process runtime composition is still unproven and must remain an acceptance gate.
7. User explicitly accepted stable-compatible OpenCode Apply behavior instead of prematurely enabling invocation-required mode without an authority provider. This reduces Deck-specific protection for this OpenCode cohort; OpenCode-native tool permissions remain. User also requires the established `sm_project_v1_<owner>_<repository>` tag for verified GitHub identity, but no Deck tag and no block solely for missing identity. The plugin manages its own fallback in non-Git/no-origin projects. Inherited tags are stripped and higher-priority project overrides are checked at the plugin's effective root, including linked worktrees.

## Verification before implementation or rollout

Use deterministic tests for SSH-config alias discovery, Git origin alias selection, fallback to the default on every unresolved case, canonical tag equivalence for verified remotes and worktrees, non-Git plugin fallback, protected secret storage, TUI redaction, installation/config preservation, per-process credential isolation, and removal of Deck-owned memory behavior. Then exercise a pinned published plugin in an isolated OpenCode session alongside Deck's execution plugin, RTK, and Context Mode MCP: stable-compatible/native permissions, thrown-hook errors, Bash rewrites, independent parent/child sessions, resume, profile switching, compaction, and the absence of Deck duplicate capture or cross-profile recalls. Do not use personal credentials or write live OpenCode configuration for the harness.
