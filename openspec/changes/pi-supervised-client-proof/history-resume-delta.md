# App-owned history / exact resume experiment

The Deck UI user approved read-only history followed by explicit supervised resume. A source-level candidate added PiResumeTarget validation, optional resume-by-id adapter/plan plumbing and an exact-target proof argument. The app remains the dependent consumer; Deck imports no UI module. Existing preparation and runtime/memory ownership remain in runRunnerLaunch.

## Historical gate: exact resume blocked (superseded below)

Review found that path validation and native SessionManager loading are not atomic. A local concurrent writer can replace a transcript while preserving its ID/cwd, bypassing an ID/path-only readiness check; missing/empty files can trigger native initialization or rewrite. No browser-supplied path exploit was demonstrated, but this violates the accepted changed-target contract. Revalidating a pathname or checking it after launch does not prove what native Pi loaded.

supportsExactPiResume() therefore returns false. The new resume-by-id mode is blocked by the adapter, source proof and exact-target launch-plan branch. The consuming app advertises no resume capability and returns 503 without launching. This is a safety gate, not a claim of a completed strict resume implementation. Legacy terminal continue/resume flags and ordinary fresh proof startup remain unchanged. No global Pi installation was patched.

Lead evidence: before gating, 38 proof/native/plan/helper tests with 151 assertions passed; this covered normal behavior, not the race. After gating, 30 affected Deck tests/97 assertions passed, including proof rejection before preparation/spawn and existing fresh launch/terminal flag behavior. App native fixtures additionally prove immutable history reads and gated rejection without a new owner. The retained positive resume fixture is explicitly skipped while unavailable.

A strict native load contract must precede enabling this mode. The app also needs persisted-context hydration after resume/reload and legacy owned-record binding. Future modification of Pi's loading boundary requires scope authorization; do not silently expand the proof or modify an installed global runner.

Official app record: ../deck-ui/openspec/changes/define-local-deck-ui/history-resume-brief.md from the Deck repository root. Read-only history itself uses app-side bounded non-mutating native-file reading and does not start Pi. At review time the live evaluation owner was not interrupted or updated. The user later explicitly authorized closure/restart to activate only the read-only history/catalog backend. Lead awaited native closure and graceful app exit, then verified history=true and resume=false with retained project/catalog metadata and no started session. This did not enable native resume or modify the global Pi installation; details are in the app-side brief.

Independent review of the later isolated strict-native candidate found blockers. Lead reproduced malformed compaction acceptance with lost ALPHA context; oversized-line and record-limit appends that cannot be reloaded strictly; and classic RPC clone rewriting an emptied fixture through an ordinary-manager replacement path despite the operation failing. The new native capability marker is not safety approval. No production activation is allowed until these are corrected and the supervised/UI path is verified. Native --help also reaches migrations/runtime construction before printing, so consumer capability probes must use isolated offline cwd/HOME/agent configuration, not real user/project roots. Current consumer integration remains experimental work in progress; the live read-only backend has not been replaced for resume. Full evidence is in the app-side history-resume brief and native ignored .artifacts/lead-native-review-repros.{mjs,log}.
