# Resilient verification — Working Brief

Status: proposed implementation plan; user-approved direction; no implementation performed here.

## Outcome and boundaries

Deck starts ordinary work despite stale Deck content, harmless formatting differences, or a newer runner. Preparation/install automatically refreshes Deck-owned skills, roles, hooks, MCP contributions and plugins. User edits survive; warnings identify the affected item while independent work continues. No reinstall instruction is the normal recovery path.

Hard refusal is reserved for an actual security boundary: authenticated credentials, enforced read-only restrictions, trusted executable/path containment, or exact Setup repair authority. Scope a refusal to the affected operation/capability; do not turn an optional capability failure into a session-wide outage. Missing executables and versions below the supported minimum remain explicit compatibility failures with an install/upgrade action, not content-verification failures.

Do not enable disabled capabilities, change model assignments, broaden tool grants, infer Setup identity from prompts/tool visibility, or silently execute user-modified hooks. Keep the documented native Codex subagent inheritance limitation and standalone Claude/Codex Setup limitation; this work does not invent missing enforcement or restore the revoked blanket PQ2 fence.

## Classification and preparation contract

- **H — self-heal:** known Deck materialization is missing/stale. Refresh from current bundled inputs and effective runner selections; validate the resulting runtime contract before launch. Reuse adapter materializers and contribution transactions, not a new installer service.
- **W — preserve + warn:** user-owned/edited content, ambiguous ownership, or a collision. Preserve the original bytes and user settings; skip only the conflicting write/contribution and continue independent work. A Deck-looking pathname or marker alone is not proof that custom contents may be overwritten.
- **B — keep hard block:** the requested operation cannot satisfy a real security boundary. Return a stable specific reason plus a safe next action (refresh/redelegate, authenticate, or restore enforceable role isolation), never the generic “reinstall everything.”
- Classify using existing receipts/previous materialization and parsed contribution semantics. Missing receipts are recoverable when current content is demonstrably an equivalent Deck contribution; reconstruct metadata without rewriting user formatting. Unknown differences are W, not automatic adoption. This is ownership reconciliation, not a general legacy compatibility layer.
- Compare parsed JSON/JSONC/TOML fields, role identity, selected capabilities, permissions and command/argument structure where semantics matter. Keep ordering where meaningful. Do not normalize arbitrary JavaScript/shell or prose into alleged equivalence: refresh known Deck content; preserve unknown edits.
- Keep hashes for provenance, transaction preimages/postimages, race detection and authenticated launch binding. A hash difference selects H/W/B; it is not itself a global refusal. Recheck security-critical material after refresh; capture a fresh descriptor rather than treating a stale descriptor as valid.
- Serialize refresh per runner installation, publish atomically, retain user originals and avoid modifying files beneath an active invocation. Reconcile at preparation/install and the next safe launch/resume boundary; repeated preparation must be idempotent. Refresh failure warns and degrades the affected optional item; block only an operation that cannot remain secure.
